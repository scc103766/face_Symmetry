# 双代理协作架构设计（v2：用户最终决策版）

> PM Agent (Hermes) ↔ 用户 (最终决策者) ↔ Engineer Agent (GPT-5.5 / Codex)

---

## 0. 核心原则

```
        ┌──────────────────────────────┐
        │     任何推进必须经过你        │
        │     "我理解了，批准"          │
        │     才能进入下一步            │
        └──────────────────────────────┘
```

**你拥有最终决定权。** Agent 是为你服务的工具，不是替你决策的代理。每一条技术路线、每一个方法选择、每一行代码的产出，都需要你先理解、再批准、再执行。

---

## 1. 架构概览

```

│         角色：决策者 · 学习者 · 最终把关人                  │

└──────┬──────────────────────────────────┬───────────────┘
       │ 需求/追问                         │ 审批/否决
       ▼                                   ▼
┌──────────────────────────┐    ┌──────────────────────────┐
│   PM Agent (Hermes) │    │  审批门 (你的判断)        │
│                           │    │                          │

│  📖 技术教师               │───▶│  • 你同意这个方法吗？      │
│  🔍 把关前置               │    │  • 可以推进了吗？         │

└──────────────────────────┘    └──────────┬───────────────┘
                                           │ 批准后
                                           ▼
                                ┌──────────────────────────┐
                                │ Engineer Agent (Hermes subagent / Codex)    │
                                │                           │
                                │  🔧 只执行已批准的任务      │
                                │  📊 完成后回报             │

                                └──────────────────────────┘
```

## 2. 三重角色定义

### 2.0 你 — 最终决策者 & 学习者

| 维度 | 说明 |
|------|------|
| 角色 | 项目所有者，一切决策的最终来源 |
| 权利 | 知情权（为什么这样做）、审批权（能否这样做）、否决权（不要这样做） |
| 责任 | 完全理解每个环节后做出判断 |
| 交互方式 | Agent 必须解释到你明白为止，你说"批准"才推进 |

**你的四种典型回应：**
- `"我理解了，批准"` → PM 将任务下发 Engineer
- `"为什么选X而不是Y？"` → PM 必须解释选型理由
- `"这个我没懂，展开讲"` → PM 用更简单的方式教学
- `"不行，换方案"` → PM 重新设计方案

### 2.1 PM Agent — 产品经理 + 技术教师 + 把关前置

| 维度 | 说明 |
|------|------|
| 运行平台 | pi agent |
| 使用模型 | DeepSeek V4 Pro (deepseek-reasoner) |
| 核心能力 | 强推理、128K+上下文、深度分析 |
| 角色1: 产品经理 | 需求拆解、架构设计、任务拆分、优先级排序 |
| 角色2: 技术教师 | 解释每个方法的原理、为什么用它、为什么它有效、替代方案对比 |
| 角色3: 把关前置 | 在提交给你之前先自审任务合理性，标记不确定点 |
| 角色4: 任务调度 | 经你批准后，PM 直接将任务写入 tasks/queue/，通知 Engineer 执行，全程驱动"下发→执行→审核"闭环 |
| 核心约束 | **未经你明确批准，不得向Engineer下发任何任务** |
| 工作文件 | `PROJECT_CONTEXT.md`（主记忆）、`docs/*.md`（技术文档） |

**PM Agent 行为准则：**
1. **先解释，再求批准**：每项技术决策必须附带清晰的教学解释
2. **不假设用户已知**：即使是基础概念，也提供简要说明或标注可展开
3. **提供备选方案**：方案A是推荐，同时列出方案B/C及其优劣
4. **标注不确定**：对把握不够的判断，明确标注"需要你决策"
5. **不做代码**：PM不直接写代码，专注于解释、建议和审核
6. **等待批准**：给出建议后必须等待你的明确批准才能推进
7. **批准后主动调度**：你批准后，PM 自动写入任务单到 queue/，通知 Engineer 执行，无需你再手动通知 Engineer

### 2.2 Engineer Agent — 执行者

| 维度 | 说明 |
|------|------|
| 运行平台 | Codex CLI |
| 使用模型 | GPT-5.5 (xhigh reasoning effort) |
| 核心能力 | 高推理努力度、代码生成、Shell执行 |
| 职责 | 代码实现、模型训练、测试、部署 |
| 核心约束 | **只执行已批准的Task，不得自行变更需求或架构** |

## 3. 审批门机制（核心）

### 3.1 两层审批

```
Layer 1: PM Agent 自审
  ├── 任务是否明确可执行？
  ├── 方法选型是否合理？
  ├── 是否与已有架构冲突？
  └── 通过后 → 提交给你（附带教学解释）

Layer 2: 你的审批（强制）
  ├── 你理解这个方法了吗？
  ├── 你同意这个方案吗？
  ├── 产出文件路径和验收标准合理吗？
  └── 通过后 → PM 下发任务给 Engineer，开始执行
```

### 3.2 审批时机

| 时机 | 需要你审批的内容 | 未经批准的行为 |
|------|-----------------|---------------|
| 新需求到达 | 需求理解是否正确、优先级是否合理 | ❌ 禁止擅自拆解任务 |
| 技术选型 | 为什么用X方法、备选方案是什么 | ❌ 禁止擅自选择技术栈 |
| 任务下发前 | 任务单内容、输入输出文件、验收标准 | ❌ 禁止擅自向Engineer下发 |
| Engineer产出后 | 代码是否符合预期、结果是否达标 | ❌ 禁止自动接受产出 |
| 里程碑推进 | 当前里程碑是否完成、是否进入下一阶段 | ❌ 禁止自动推进里程碑 |
| **任务下发** | **经你批准后，PM 直接将任务写入 queue/ 并通知 Engineer，无需你手动操作** ✅ |

### 3.3 审批对话格式

PM Agent 向你请求审批时使用以下格式：

```
## 📋 需要你审批：[审批事项]

### 要做什么
[一句话描述]

### 为什么这样做
[教学解释：原理、选型理由、替代方案对比]

### 具体任务
| 输入 | 输出 | 验收标准 |
|------|------|---------|
| ... | ... | ... |

### 风险与不确定点
- [需要你特别关注的地方]

### 请回复
- "批准" → 立即执行
- "展开讲 [具体点]" → 我进一步解释
- "换方案，考虑 [你的想法]" → 重新设计
- "先缓缓" → 暂停，等待你后续指示
```

## 4. 教学解释规范

### 4.1 何时需要解释

PM Agent 在以下场景必须提供教学解释：

| 场景 | 解释深度 |
|------|---------|
| 选择算法/模型（如XGBoost vs 随机森林） | 原理+优劣对比+为什么选它 |
| 引入新工具/库（如SHAP、FastAPI） | 它是干什么的+为什么需要它 |
| 设计架构决策（如晚期融合vs早融合） | 两种路线的逻辑+各自适用场景 |
| 数据处理方法（如SMOTE、归一化） | 解决了什么问题+不用会怎样 |
| 评估指标选择（如AUC vs F1） | 每个指标的含义+为什么用这个 |

### 4.2 解释格式要求

```
## 📖 技术解释：[主题]

### 一句话总结
[让非技术背景也能理解的一句话]

### 它在解决什么问题
[问题的本质]

### 它是怎么工作的
[分步骤讲清楚，用类比帮助理解]

### 为什么在这个项目中用它
[结合本项目具体场景说明]

### 替代方案及为什么不选
| 方案 | 优势 | 为什么不选 |
|------|------|-----------|
| ... | ... | ... |

### 如果不用它会怎样
[缺失的后果]
```

## 6. Engineer 开发日志（强制）

> **Engineer 每完成一个任务，必须输出结构化开发日志。**
> PM Agent 审核日志质量后，连同自己的解读一起提交给你。

### 6.1 为什么需要开发日志

你作为最终决策者和学习者，需要看到 Engineer 的开发过程，而不只是一个结果。开发日志让你：
- **理解Engineer做了什么** — 不只是"完成了"，而是"怎么做完的"
- **理解为什么这样做** — 设计选择背后的考量
- **看到代码变更** — 新增了哪些文件、修改了哪些文件
- **看懂核心逻辑** — 关键代码是干什么的、怎么工作的
- **判断质量** — 开发思路是否合理、有没有隐患

### 6.2 开发日志格式（Engineer 必须按此输出）

```markdown
## 🛠️ 开发日志 — 任务单 #[编号]

### 📝 开发过程（分步骤）
1. [步骤1：做了什么，为什么]
2. [步骤2：做了什么，为什么]
3. ...

### 🧠 开发思路
**整体设计考量**：[架构为什么这样设计]
**为什么选择这个实现方式**：[比如为什么用类而不是函数、为什么用这个库]
**与其他模块的关系**：[这段代码在整个项目中扮演什么角色]

### 📊 代码变更清单
| 操作 | 文件路径 | 说明 |
|------|---------|------|
| 新增 | `src/models/xxx.py` | [这个文件是干什么的] |
| 修改 | `src/data/loader.py` | [改了什么、为什么改] |
| 删除 | — | — |

### 💡 核心代码解读

#### 关键代码块1：[功能描述]
``` python
# 实际代码
```
**解读**：[这段代码做了什么，逐部分解释]
**为什么这样写**：[设计考量、有没有其他写法、为什么选这种]

#### 关键代码块2：[功能描述]
...

### ⚠️ 遇到的问题与解决方案
| 问题 | 原因 | 解决方案 | 是否完全解决 |
|------|------|---------|------------|
| ... | ... | ... | ✅/⚠️ |

### 📚 参考来源
- [参考了哪个文件/文档/StackOverflow]
```

### 6.3 PM Agent 对开发日志的处理

PM Agent 在收到 Engineer 的开发日志后：
1. **自审日志质量**：是否完整、核心代码解读是否清晰
2. **补充PM视角解读**：用通俗语言向用户翻译技术细节
3. **标注重点**：哪些是用户需要特别关注的
4. **提交用户审核**：日志 + PM解读一并呈现

### 6.4 用户如何审阅开发日志

| 你想知道的 | 看日志的哪个部分 |
|-----------|---------------|
| Engineer做了什么 | 📝 开发过程 |
| 为什么这样做 | 🧠 开发思路 |
| 改了什么文件 | 📊 代码变更清单 |
| 核心逻辑怎么写的 | 💡 核心代码解读 |
| 有没有踩坑 | ⚠️ 遇到的问题与解决方案 |
| 宏观理解 | 📖 PM解读 |

## 7. 工作流程（含审批门）

```
用户提出需求
    │
    ▼
PM Agent 读取 PROJECT_CONTEXT.md
    │
    ▼
PM Agent 分析需求
    │
    ├── 需要澄清 → 追问用户
    │
    └── 理解明确
            │
            ▼
        PM Agent 设计方案 + 教学解释
            │
            ▼
        PM Agent 向你提交审批
            │
    ┌───────┴────────┐
    │ 你的审批        │
    ├────────────────┤
    │ 批准  │ 追问/否决/修改 │
    └───┬───┴────┬──────────┘
        │        └→ PM重新设计/解释
        ▼
    PM Agent 下发任务单给 Engineer
    （写入 tasks/queue/，通知 Codex 读取执行）
        │
        ▼
    Engineer Agent 执行
        │
        ▼
    Engineer Agent 回报 PM
        │
        ▼
    PM Agent 解读产出 + 提交你审核
        │
    ┌───┴───────────┐
    │ 你的审核        │
    ├───────────────┤
    │ 通过  │ 退回修改 │
    └───┬───┴────┬────┘
        │        └→ PM传达修改意见给Engineer
        ▼
    PM 更新 PROJECT_CONTEXT.md
        │
        ▼
    PM 通知你：本任务完成，下一任务是什么？
```
