# Hermes PM 断点恢复执行细则

用于 PM 工作模式中“继续已下发任务 / 恢复执行”的场景，尤其是 tasks/queue 中已有任务但 tasks/done 没有对应报告时。

## 恢复前检查顺序

1. 先读 `WORK_STATUS.md`，确认当前阶段、任务编号、最后摘要。
2. 对比 `tasks/queue/`、`tasks/done/`、`tasks/rejected/`：
   - queue 有任务且 done 无报告 → 任务未完成或未回报。
   - done 有报告 → 先读报告，不要重复执行。
3. 搜索任务要求的实际产物：目录、映射文件、模型权重、报告、集成代码。
4. 对数据型任务先验证数据就绪状态，再判断是否可执行。
5. 汇总“已有产物 / 缺失产物 / 阻塞点 / 建议恢复点”，让用户审批下一步。

## 安全恢复原则

- 不要一上来执行长耗时全量任务。先做最小闭环：clone/check、生成映射、路径完整性、少量 smoke test、报告。
- 对全量预处理、训练、下载、安装依赖、大量写文件等操作，必须拆成阶段并单独审批。
- 如果用户用简写批准（如 `A1`），而下一步会创建或修改项目文件，要求明确授权：`批准 A1`。
- 用户明确说“批准 <方案>”后再执行。
- 若命令被审批系统拒绝，不要绕过或改写重试；停止并汇报已完成项、阻塞项、尚未写入的报告。
- 只有验证项真正完成后，才写 `tasks/done/<task>_report.md`；未完成则汇报“部分完成”，不要标记 done。

## 阶段化 Smoke Test 模式

当恢复点是高成本数据/模型流水线（全量预处理、训练、下载、批量写缓存）时，采用“原任务不直接全量执行，先创建字母后缀子任务”的阶段化模式：

1. 原始大任务保留在 `tasks/queue/` 作为背景，不直接删除或标记完成。
2. 设计低风险子任务，如 `M2-02a`、`M2-02b`：
   - `a` 通常做 5-10 个样本 smoke test，验证 I/O、依赖、数据形状、缓存写出。
   - `b` 通常修复/引入正式后端后复测，或扩大到 100 样本。
   - 全量任务必须在 smoke test 报告通过后另行审批。
3. 子任务必须有清晰边界：样本数、最大帧数、输出目录、是否允许安装/下载/训练。
4. 子任务成功后写 `tasks/done/task_<子任务>_report.md`，并更新 `WORK_STATUS.md` 到下一个待审批点。
5. 报告中必须区分“smoke test 成功”与“最终论文级/生产级链路已完成”。如果用了 fallback、近似算法或临时后端，要显式写入缓存和报告，避免未来误用为正式训练特征。

## 最小闭环报告应包含

- 实际执行的命令/脚本概览。
- 创建或修改的文件。
- 数据完整性统计（行数、缺失数、分组泄漏等）。
- smoke test 结果。
- fallback/临时实现说明（如有）：说明它验证了什么、不能替代什么。
- 未完成项和明确阻塞点。
- 下一步建议和是否需要用户再次审批。
