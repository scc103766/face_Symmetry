# 技术文档交付：通用说明型 vs 项目专属方案

## 触发场景

用户要求生成技术方案、说明文档、调研汇总、md/docx 文件，尤其是：

- “先写一个 md 文件再保存为 docx”
- “这是说明型文档，不要写项目内部编号”
- “再生成一个包含项目专属表述的方案”
- “重点突出从技术角度如何防范各类攻击”

## 关键判断：文档定位

### 通用说明型文档

写法：

- 讲通用技术原理、行业攻击类型、防护机制、模型/数据/评测方法。
- 不写内部服务号、checkpoint、端口、实验目录、项目名、内部固定编号。
- 若用户明确要求“普适”“说明型”，需要主动验证禁用关键词不存在。

禁用词示例按项目动态调整，例如本次包括：

- `18131`
- `Face Liveness Detection`
- `flash-liveness`
- `当前项目`
- `本项目`
- `V3`
- `YOLO`

### 项目专属方案

写法：

- 可以写项目名、服务号、模型版本、端口、权重路径、协议名、采集/推理服务、GPU/环境约束。
- 适合落地实施、训练计划、服务集成、API 字段、项目目录中的交付文档。
- 仍要区分“已完成事实”和“建议方案”，避免把计划写成已实现。

## 技术防护型文档推荐结构

当用户强调“从技术角度防范攻击”时，用下面结构优先于单纯论文/攻击罗列：

1. 背景与目标
2. 威胁模型
3. 攻击与防护技术对应关系
   - 攻击类型
   - 防护目标
   - 核心技术手段
   - 输出风险信号
4. 总体防护架构
5. 分攻击类型的技术实现
6. 数据与标签体系
7. API 输出设计
8. 模型训练与工程路线
9. 评测体系
10. 工程落地优先级
11. 结论

示例表头：

```markdown
| 攻击类型 | 防护目标 | 核心技术手段 | 输出风险信号 |
|---|---|---|---|
| 打印照片 | 判断是否为平面纸质介质 | 闪光响应曲线、局部高光、CDC/LBP、频域残差 | photo_spoof_score |
```

## md -> docx 交付流程

1. 写入同名 Markdown 源文件。
2. 转换为 docx。
   - 优先 pandoc/libreoffice；不可用时可用 Python 生成最小 docx zip 包。
3. 验证：
   - md 存在、行数、大小；
   - docx 存在、大小；
   - zip 结构 `testzip()` 通过；
   - 必要 parts 存在：`[Content_Types].xml`、`_rels/.rels`、`word/document.xml`、`word/styles.xml`；
   - `file <docx>` 显示 Microsoft Word 2007+。
4. 若用户要求通用/项目专属，额外验证关键词：
   - 通用说明型：禁用项目专属关键词；
   - 项目专属方案：确认包含项目专属关键词。

## 汇报格式

最终回复应包含：

- Markdown 绝对路径；
- DOCX 绝对路径；
- 验证结果；
- 关键修改点/核心章节；
- 若有 caveat，说明哪些内容是建议、哪些是已实现事实。
