# Hermes 上下文 Agent 机制（PM 冷启动恢复）

当 PM 工作模式中的单次 Hermes 对话接近模型上下文窗口上限时，使用本机制避免压缩导致项目背景、审批链条和技术决策丢失。

## 核心原则

不要把“完整聊天原文”作为下一轮上下文。把已经结构化归档的项目状态作为下一轮上下文：

1. `PROJECT_CONTEXT.md` — 长期项目主记忆：目标、边界、技术路线、里程碑、关键决策。
2. `WORK_STATUS.md` — 当前断点仪表盘：当前任务、阶段、待审批、技术债、最近会话。
3. `sessions/project/` — 项目推进历史：需求、方案、任务、结果、决策证据。
4. `sessions/meta/` — 工具/知识/配置历史：Hermes、skills、环境、知识问答。
5. `tasks/` — PM/Engineer 执行队列：queue/done/rejected。

新 Hermes Agent 不继承旧长对话，而是从这些文件恢复项目状态。

## 触发条件

本项目按 **272k token** 作为模型上下文硬上限。PM 应在以下任一情况触发提示：

- Hermes/CLI 或模型提示上下文即将压缩或接近窗口上限。
- `/usage` 或其他 token 信息显示接近 250k~260k。
- 对话已经包含大量工具输出、长文件内容、长报告，继续推进会导致早期内容被压缩。
- PM 发现自己开始依赖“聊天记忆”而不是项目文件来判断状态。

触发时必须先停下并询问用户：

```text
当前上下文接近 272k 限制，继续对话可能触发压缩并丢失早期细节。
是否开启 Hermes 上下文 Agent 机制？

开启后我会先归档当前对话、更新 WORK_STATUS.md，然后用 PROJECT_CONTEXT.md + WORK_STATUS.md + 最近相关 session 作为新 Hermes PM Agent 的启动上下文。
```

用户未批准前，不要自动开启新 Agent，也不要继续做大范围项目推进。

## 开启后的交接流程

用户批准后按顺序执行：

1. **冻结当前推进点**
   - 明确当前正在做什么。
   - 明确哪些任务已完成、哪些只是建议、哪些等待审批。
   - 不再启动新的长任务。

2. **归档当前对话**
   - 项目推进写入 `sessions/project/YYYY-MM-DD_简短描述.md`。
   - 工具/知识/配置写入 `sessions/meta/YYYY-MM-DD_简短描述.md`。
   - 如果同一对话两类都有，拆成两个 session。
   - 每个 session 必须以 `## ✅ 会话完成` 或 `## ⚠️ 会话中断` 结束。

3. **更新 `WORK_STATUS.md`**
   - `🔄 当前进行中` 写清当前断点。
   - `📋 待审批队列` 写清用户下一步要批准什么。
   - `📝 最近会话记录` 加入刚写的 session。
   - `🔧 待处理异常 / 技术债` 记录阻塞项。

4. **必要时同步 `PROJECT_CONTEXT.md`**
   - 只同步稳定项目事实：技术路线、里程碑状态、关键决策、数据集状态、边界变化。
   - 不要把临时讨论、工具报错、一次性命令写入长期主记忆。

5. **生成新 Hermes 启动输入**
   - 给用户一段可以直接复制到新 Hermes 的 prompt。
   - prompt 要指定项目目录、恢复文件、当前断点和审批规则。

6. **新 Hermes 启动后先恢复，不执行**
   - 新 Agent 先读文件和汇报断点恢复检查。
   - 未经用户明确“批准/通过”，不得执行代码改动、安装、训练、下载或下发 Engineer 任务。

## 标准新 Hermes 启动 Prompt

通用版：

```text
开启 PM 工作模式。

当前项目目录：
/path/to/project

请先加载 pm-workflow skill，然后按以下顺序恢复上下文：
1. 读取 PROJECT_CONTEXT.md，理解项目目标、技术路线、里程碑。
2. 读取 WORK_STATUS.md，判断当前断点、待审批事项和技术债。
3. 扫描 sessions/project/ 和 sessions/meta/，只读取最近相关 session。
4. 扫描 tasks/queue、tasks/done、tasks/rejected，确认任务队列状态。
5. 输出断点恢复检查，不要直接推进开发任务。
6. 未经我明确说“批准/通过”，不得执行代码改动或下发 Engineer 任务。
```

带明确恢复点版：

```text
开启 PM 工作模式，继续 <项目名>。

当前项目目录：
/path/to/project

请读取：
- PROJECT_CONTEXT.md
- WORK_STATUS.md
- sessions/project/<最近项目推进session>.md
- sessions/meta/<如相关的最近meta session>.md
- tasks/done/<最近任务报告>.md
- tasks/queue/

目标：恢复到 <当前待审批点>。
请先汇报当前状态、证据文件、阻塞点和建议方案，不要直接执行。
未经我明确说“批准/通过”，不得修改代码、安装依赖、启动训练或下发 Engineer 任务。
```

## 为什么不用完整聊天原文

完整聊天原文有大量噪声：工具输出、失败尝试、临时解释、重复确认、未批准的方案。新 Agent 如果直接读完整原文，容易把“讨论过”误判为“已批准”，或者把临时想法当成项目事实。

结构化恢复更可靠：

- `PROJECT_CONTEXT.md` 只存长期事实。
- `WORK_STATUS.md` 只存当前断点。
- `sessions/` 存历史证据。
- `tasks/` 存执行状态。

这让新模型从项目状态理解流程，而不是从聊天噪声猜测流程。

## 归档质量要求

开启上下文 Agent 机制前，当前会话归档必须满足：

- [ ] project/meta 分类正确。
- [ ] 每个 session 有完成或中断标记。
- [ ] `WORK_STATUS.md` 当前阶段准确。
- [ ] 待审批事项不是空泛描述，而是用户可以直接回复“批准 X”的具体方案。
- [ ] 最近任务报告路径写明。
- [ ] 新 Hermes 启动 prompt 可直接复制使用。

## 常见错误

1. **只复制最后一轮聊天给新 Agent。** 这仍然依赖聊天上下文，不是冷启动恢复。
2. **归档前没有更新 WORK_STATUS.md。** 新 Agent 会找不到当前断点。
3. **把 meta 内容混进 project。** 工具/skill 配置会污染项目推进历史。
4. **把未审批方案写成已决定。** 归档时必须区分“建议/待审批/已批准/已执行”。
5. **新 Agent 启动后直接执行。** 新 Agent 第一件事永远是恢复检查和汇报，不是执行。
